# v0.3.0 卡池、BAN 与定向抽取核验

核验日期：2026-10-16，按 `.9` 候选最终生成数据重新枚举。结论：保留莱茵、卡兹戴尔、雷姆扩展，石棉新增【独行】且不恢复【坚守】后，1–4 人采用核心 6、附加 6 的全局 BAN 仍可行；必须保留每阶至少 8 种共享商店干员的运行时约束。标准模拟对应核心 3、附加 3。本核验没有修改用户服务器，也不代表 Windows 实机或多人试玩验证。

## 可刷定义与精确枚举

脚本直接复用 [pool.js](../server/match/pool.js) 的 `isOpeningShopChess`、`openingTierCounts`、`OPENING_TIER_FLOOR`，与运行时保底采用相同筛选：可见、普通基础形态、非 DIY、非隐藏、整数 I–VI 阶，且 `gd.poolCopies(id) > 0`。每种以基础棋子 ID 计一次，库存份数不增加“种数”。私人自选库不计入全队共享保底。

令 D 为抽到的盟约，S 为模式静态关闭的盟约。一名具有盟约的干员仅当其**所有**盟约都属于 `D ∪ S` 时被禁用；无盟约记录不因空集合判定而被禁用。正权重且非静态关闭的核心与附加盟约分别选取固定数量，不重复选取。模式或插件修改卡池、库存、盟约或静态关闭列表时，运行时重新计算；不得硬编码本文的 134 种。

本次未施加模式静态关闭与随机 BAN 前，共享商店有 **134 种**，I–VI 阶分别为 **20 / 22 / 23 / 25 / 23 / 21**。

## v0.3.0 抽取语义与概率边界

相关路径为 [gamedata.js](../server/match/gamedata.js)、[player/diy.js](../server/match/player/diy.js)、[player/economy.js](../server/match/player/economy.js)、[pool.js](../server/match/pool.js)、[effectsMeta.js](../server/match/effectsMeta.js)、[builtinMeta.js](../server/match/builtinMeta.js)。上游变更依据见 [0.3.0 历史 §32.14.24、§32.14.31、§32.14.32](history/0.3.0.md)。

- 共享池合作库存仍为单人份数的 2 倍，与队伍人数无关。v0.3.0 的新变化是**每位玩家自己的自选库存也翻倍**：V 阶 16、VI 阶 10；单人仍为 8、5。私库只供该玩家抽取，不进入全队共享库存。
- DIY 参与普通商店和随机赠送是已有行为，不能称为 v0.3.0 新增。所有自身盟约均关闭的自选干员仍无私库。普通商店还要求达到该槽的 `shopLevel`；晋升奖励与随机赠送按各自的等阶规则筛选。
- 普通商店每个干员格直接从“等阶不高于商店等级”的剩余份数加权抽取，包含该玩家当时符合条件的私库；不是先均匀选阶，再均匀选干员。显示不预占份数，同一次刷新可以重复。
- 对某一确定状态，目标单格概率为 `目标合格剩余份数 /（合格共享剩余份数 + 该玩家合格私库剩余份数）`。在份数和筛选条件不变、独立抽取 n 格时，至少出现一次的概率为 `1 - (1 - p)^n`。BAN 结果、商店等级、自选名单、已持有份数和来源筛选缺一时，不提供虚构的固定抽中率。旧按合作私库 8/5、忽略私库或按种数均分的估算应重算。
- 简易通讯机沿原 `rollSameBond → rollChess → grantChess` 路径，限商店等级及同盟约，随机范围包含符合条件的该玩家私库；正常共享干员消耗共享池，自选消耗自己的私库。池已空则不凭空补人。`acquireChess` 本身允许已展示卡透支，不可绕过 `grantChess` 的存量检查来实现通讯机抽人。
- v0.3.0 允许已展示的装备商店卡、奖励卡在库存耗尽后领取并记录债务；新抽取及普通赠送仍受库存限制，未选奖励会保留到后续准备阶段。R3/R7 通讯机采用独立系统补给，仅发放来源独立；这不应放开其他装备库存，也不应把通讯机抽出的干员改为无限库存。

本审计证明批准的 BAN 数量与当前卡池的逐阶约束兼容，没有测量新增商店格、通讯机或战斗平衡的实际胜率。源码回归、Windows 安装与升级、发行附件一致性由发布验证另行记录。
